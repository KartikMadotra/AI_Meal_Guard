AI MealGuard: Complete Team Brief & Technical Log

This document serves as the master blueprint for the AI MealGuard project. It contains the high-level explanations for presentations, as well as the deep technical theory, algorithms, and flowcharts required for comprehensive academic logbooks.

1. Executive Summary (The One-Minute Explanation)

(Every team member should memorize this core concept)

AI MealGuard is an AI-based school meal monitoring system designed around SDG 2 — Zero Hunger. It uses computer vision to identify food components on a student's plate, uses segmentation to locate individual food regions, estimates approximate quantities, calculates nutritional values using a nutrition database, compares them against selected age-group requirements, generates a meal-quality score, provides recommendations, and stores meal records for historical analysis.

2. Problem Statement & SDG 2 Connection

School meals are intended to provide adequate nutrition, but monitoring portions and nutritional quality manually is difficult. AI MealGuard is designed to improve transparency and monitoring of school meal distribution, ensuring that every child receives the required nutrients to support their developmental age.

6. Deep Technical Theory: Algorithms & Mathematics (For Logbook)

This section provides the hardcore theoretical backing for the logbook, detailing how the model functions internally and the mathematical formulas used for estimation.

A. YOLOv8 Architecture Overview

Our system uses YOLOv8-seg. Unlike older models, YOLOv8 is an anchor-free model that uses a modified CSPDarknet53 backbone to extract features at various scales. These features are passed through a Path Aggregation Network (PANet) neck. The crucial innovation in the segmentation head is that it outputs two things: a set of prototype masks (which span the whole image) and a set of mask coefficients for each detected bounding box. The final polygon is generated by linearly combining the prototypes using the coefficients and cropping it to the bounding box.

B. The Weight Estimation Algorithm (Pixel Area Math)

To avoid requiring physical weighing scales, the system uses 2D spatial analysis to estimate food volume and weight. The mathematical formula implemented in ai_service.py is:

Area_Fraction = Pixel_Area_of_Mask / Total_Image_Pixels
Estimated_Weight (g) = Area_Fraction × MAX_IMAGE_WEIGHT_CAPACITY × Density_Factor

Variables:

  • Pixel_Area_of_Mask: Derived directly from the contour of the YOLOv8 polygon using OpenCV (cv2.contourArea).
  • MAX_IMAGE_WEIGHT_CAPACITY: A calibrated constant (e.g., 1500g) representing the maximum weight the camera view can hold if full.
  • Density_Factor: A hardcoded multiplier based on the specific food (e.g., Dal is dense/heavy = 1.2, Roti is light/flat = 0.5).

C. Evaluation Metrics Math

The model's performance was evaluated using standard Object Detection metrics:

Precision = True_Positives / (True_Positives + False_Positives)
Recall = True_Positives / (True_Positives + False_Negatives)
IoU (Intersection over Union) = Area_of_Overlap / Area_of_Union
mAP50 = Mean Average Precision across all classes at an IoU threshold of 0.50.

9. What is Our Innovation?

Our contribution to solving this problem consists of:

  1. Food-specific dataset curation and manual labeling using polygons.
  2. Custom YOLOv8 food instance segmentation model (not just bounding boxes).
  3. School-meal recognition workflow explicitly tied to SDG 2.
  4. Visual quantity estimation approach using Pixel Area Density scaling.
  5. Age-aware nutritional assessment (A 15-year-old is graded differently than a 7-year-old).
  6. Dynamic meal scoring system (0-100 scale).
  7. Explainable nutritional recommendations based on macro deficits.
  8. Anti-Scam historical meal tracking database.
  9. School-level analytics dashboard for administrative oversight.
  10. A complete, working end-to-end prototype deployed via FastAPI.

10. Limitations & Future Scope

Current Limitations

  • Food quantity is estimated based on 2D area, not measured by a physical 3D weighing scale.
  • Similar-looking foods (e.g., various brown curries) may sometimes be confused.
  • Poor lighting can significantly reduce detection quality.
  • Occluded/overlapping food can be difficult to segment accurately.
  • Nutrition values depend entirely on the provided JSON database averages.
  • Portion estimation depends on a consistent camera setup and distance calibration.
  • The system is a monitoring/screening prototype, not a laboratory food-safety test.
  • Results should be reviewed by humans when AI confidence is low.

13. Deep Technical Details (Dataset & Backend Architecture)

A. Dataset Curation & Preprocessing

The foundation of this project is a heavily modified version of the IIIT-Delhi Indian Thali Dataset. While the original dataset provided bounding boxes, instance segmentation requires polygon masks. Our team undertook the massive effort to manually annotate or refine polygons for Indian food classes. During Phase 4 of training, we discovered a critical label mismatch: the directory contained 50 classes, but our data.yaml was strictly mapped to 41 classes. We wrote custom Python parsing scripts to align the label integers in the text files, avoiding indexing errors during PyTorch dataloading.

B. Backend Architecture (FastAPI Asynchronous Routing)

The backend is built on FastAPI using Uvicorn as the ASGI server. We chose FastAPI over Flask/Django for two reasons:

  • Asynchronous execution: YOLO inference is heavily blocking. By using async def endpoints, the server can handle multiple plate requests concurrently without freezing.
  • Pydantic Models: All Base64 images and nutritional data are strictly validated using Pydantic, ensuring type safety before it ever hits the YOLO engine.

C. Nutritional Data Structures (age_requirements.json)

The logic engine relies on a strict JSON schema to evaluate meals. Instead of hardcoding logic, we structured age_requirements.json to dynamically adjust thresholds. For example, a 7-9 year old requires 450 Calories and 12g of Protein for a midday meal, whereas a 13-15 year old requires 700 Calories and 20g of Protein. The logic engine parses the student's age, dynamically loads these baseline arrays, and mathematically compares them against the YOLO estimated weights to generate the 0-100 score.
